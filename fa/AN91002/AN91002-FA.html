در محیط کامپایلر MRS، پیکربندی فایل‌های LD و فایل راه‌اندازی می‌تواند تخصیص حافظه، ذخیرۀ در نشانی ثابت، متغیر مشترک، انتقال و نشانی‌گیری برای اجرا و موارد مشابه را به‌صورت انعطاف‌پذیر پیاده کند و تا حدی انعطاف‌پذیری کاربرد پروژه را بالا می‌برد.

◆توضیح مختصر فنی

این بخش افزودۀ مترجم برای درک بهتر مفاهیم سند است و در متن اصلی وجود ندارد.

۱. فایل LD چیست؟

فایل LD اسکریپت پیوند (Linker Script) است که به پیوندگر می‌گوید کد و داده را کجا بچیند. بخش MEMORY نواحی حافظه را با نشانی آغازین (ORIGIN) و اندازه (LENGTH) تعریف می‌کند و بخش SECTIONS ورودی‌های کامپایل‌شده را به این نواحی می‌چینند؛ نشانی‌های نهایی برنامه از همین‌جا می‌آیند.

۲. فایل راه‌اندازی چیست؟

فایل راه‌اندازی (Startup) کد اسمبلی‌ای است که پیش از ورود به تابع اصلی اجرا می‌شود: ویژگی بخش‌ها و جدول بردار را تعریف می‌کند، داده بخش .data را از فلش به RAM منتقل می‌کند، بخش .bss را صفر می‌کند و ثبات‌های هسته (حالت کار، ممیز شناور، پشته‌سازی سخت‌افزاری) را تنظیم می‌کند.

۳. انتقال به RAM و اجرا

در تراشه‌های سری H417 اجرای مستقیم از فلش (فلش صفرمکث) امکان‌پذیر اما نسبتاً کند است؛ بنابراین طرح رایج این است که کد در فلش باقی بماند اما در راه‌اندازی به ناحیه‌ای از RAM (بخش RAM_CODE) منتقل شود و از آن‌جا با سرعت بالا اجرا شود. دو نشانیِ «اجرا» (VMA) و «بارگذاری» (LMA) که با دستور AT> جدا می‌شوند، مبنای این انتقال‌اند.

تخصیص حافظه و پیکربندی سیستم

◆۱.۱ طرح تخصیص حافظۀ H417

در فایل LD، بخش MEMORY نشانی آغازین و اندازۀ تخصیص حافظۀ تراشه را تعریف می‌کند. توجه شود که نخست بازه‌های حافظۀ تعریف‌شده نباید هم‌پوشانی داشته باشند؛ و دوم نباید از محدودۀ واقعی حافظه فراتر بروند؛ در غیر این صورت خطای کامپایل یا رفتار غیرعادی برنامه رخ می‌دهد.

در ادامه برای توضیح دقیق‌تر از H417 مثال می‌زنیم. تخصیص حافظۀ H417 انعطاف‌پذیر اما نسبتاً پیچیده است؛ به‌طور پیش‌فرض نشانی‌گیری و اجرا از FLASH انجام می‌شود که سرعت اجرا نسبتاً کند است؛ بنابراین نمونه‌ها همگی طرح انتقال به RAM و اجرا از آن را ارائه می‌دهند. در عمل می‌توان بسته به نیاز پروژه، اندازه و محل حافظۀ V3 و V5 را دوباره تخصیص داد. در زیر نمای انتزاعی عمومی تخصیص پروژه‌های V3 و V5 آمده است.

V3: MEMORY { /*FLASH, RAM, and RAM-CODE can be freely configured according to project requirements;Please refer to the datasheet manual for specific allocation*/ FLASH (rx) : ORIGIN = A, LENGTH = SIZE_A /* zero_wait flah ,and loaded into RAM_CODE for running */ RAM_CODE (xrw) : ORIGIN = B, LENGTH = SIZE_B /* RAM for running code*/ RAM (xrw) : ORIGIN = C, LENGTH = SIZE_C /* RAM for .data .bss section and other*/ RAM_LOAD (xrw) : ORIGIN = D, LENGTH = SIZE_D /* RAM for .load section*/ } V5: MEMORY { /*FLASH, RAM, and RAM-CODE can be freely configured according to project requirements;Please refer to the datasheet manual for specific allocation*/ FLASH (rx) : ORIGIN = E, LENGTH = SIZE_E /* zero_wait flah ,and loaded into RAM_CODE for running */ RAM_CODE (xrw) : ORIGIN = F, LENGTH = SZIE_F /*ITCM RAM for running code*/ RAM (xrw) : ORIGIN = G, LENGTH = SIZE_G /*DTCM RAM for .data .bss section and other*/ RAM_LOAD (xrw) : ORIGIN = H, LENGTH = SIZE_H /* RAM for .load section*/ }
شکل ۱تخصیص حافظۀ 417 (برچسب‌ها مطابق سند اصلی)

پارامترهای V3:

A: معمولاً برابر 0x00000000 یعنی آغاز FLASH است؛ SIZE_A: اندازۀ FLASH تخصیصی V3. (لازم)

B: نشانی آغاز انتقال V3 به RAM؛ SIZE_B: اندازۀ کد انتقالی V3؛ اشغال واقعی تقریباً برابر اندازۀ بخش FLASH است (اندکی کمتر، چون بخشی از محتوا مانند بخش .data در Section<RAM> قرار می‌گیرد)؛ بنابراین اندازه را SIZE_B = SIZE_A تخصیص دهید. (اختیاری)

C: بخش‌های .data و .bss؛ در نشانی آغاز باید توجه داشت که پیش از آن، بخش‌های Section<RAM_CODE> و Section<RAM_LOAD> قرار دارند؛ بنابراین شرط C >= B+SIZE_B+SIZE_D باید برقرار باشد؛ SIZE_C: اندازۀ تخصیص Section<RAM>؛ به‌عنوان مثال در 417، شرط C + SIZE_C <= 0x20180000 (نشانی انتهای SRAM). (لازم)

D: بخش پیش‌بارگذاری؛ هدف آن انتقال کد در RAM است؛ پیش از بخش Section<RAM_LOAD>، بخش Section<RAM_CODE> قرار دارد؛ بنابراین شرط D >= B + SIZE_B؛ SIZE_D: اندازۀ کدِ بارگذاری؛ اگر محتوای پیش‌بارگذاری در فایل راه‌اندازی افزایش یابد ممکن است خطای کامپایل رخ دهد؛ در این صورت کافی است SIZE_D را بزرگ‌تر کنید. (اختیاری)

پارامترهای V5:

E: نشانی آغاز FLASH تخصیصی V5؛ معمولاً شرط E >= A + SIZE_A؛ SIZE_E: اندازۀ FLASH تخصیصی V5. (لازم)

F: نشانی آغاز انتقال V5 به RAM (پیشنهاد می‌شود از ناحیۀ پیوند نزدیک استفاده شود)؛ SIZE_F: اندازۀ کد انتقالی V5؛ اشغال واقعی تقریباً برابر اندازۀ بخش FLASH است؛ بنابراین اندازه را SIZE_F = SIZE_E تخصیص دهید. (اختیاری)

G: بخش‌های .data و .bss؛ در نشانی آغاز باید توجه داشت که پیش از آن، Section<RAM_CODE> (ITCM)، نشانی پشته‌سازی سخت‌افزاری (پیش‌فرض اما قابل پیکربندی) و Section<RAM_LOAD> (DTCM) قرار دارند؛ SIZE_G: اندازۀ تخصیص Section<RAM>. (لازم)

H: بخش پیش‌بارگذاری در ناحیۀ پیوند نزدیک DTCM؛ باز هم انتقال کد در RAM انجام می‌شود؛ پیش از بخش Section<RAM_LOAD> نشانی پیش‌فرض پشته‌سازی سخت‌افزاری قرار دارد؛ بنابراین شرط H >= DTCM_BASE + 512B (اشغال پشته‌سازی سخت‌افزاری)؛ SIZE_H: اندازۀ کدِ بارگذاری؛ اگر محتوای پیش‌بارگذاری در فایل راه‌اندازی افزایش یابد ممکن است خطای کامپایل رخ دهد؛ در این صورت کافی است SIZE_H را بزرگ‌تر کنید. (اختیاری)

مورد خاص: در شرایط خاص، وقتی هستۀ V5 حافظۀ زیادی مصرف می‌کند، می‌توان ITCM و بخشی از ناحیۀ پیوند نزدیک DTCM را برای نشانی‌گیری و اجرا به کار برد. توجه شود که برای تخصیص DTCM باید 512B برای پشته‌سازی سخت‌افزاری هستۀ V5 رزرو شود و نشانی پشته‌سازی سخت‌افزاری نیز باید دوباره تنظیم شود (در حالت Machine خواندنی/نوشتنی).

◆۱.۲ طرح پیکربندی سیستمی H417

فایل راه‌اندازی تراشه‌های با هستۀ RISC-V، کارکردهای اصلی زیر را بر عهده دارد: تعریف ویژگی بخش‌ها (Section)، تعریف جدول بردار، بارگذاری داده و پیکربندی ثبات‌های هسته و حالت کار تراشه و غیره. تعریف ویژگی بخش‌ها اغلب باید همراه نشانی متناظر در فایل LD باشد تا اثر معقول داشته باشد. بارگذاری داده شامل بارگذاری داده بخش‌های data/highcode و صفرکردن بخش bss است. تغییر ثبات‌های هسته شامل تنظیم حالت کار تراشه، کلید روشن/خاموش‌کردن کارکرد ممیز شناور، تنظیم پشته‌سازی سخت‌افزاری و تعداد سطوح تودرتوی آن و غیره است. ثبات‌های هسته‌ای که در حالت Machine خواندنی/نوشتنی‌اند تقریباً همگی را می‌توان در فایل راه‌اندازی پیکربندی کرد؛ برای محتوای مشخص به کتابچۀ هستۀ متناظر مراجعه کنید.

◆۲.۱ ذخیرۀ داده در بخش حافظۀ مشخص

فایل راه‌اندازی تراشه‌های با هستۀ RISC-V، کارکردهای اصلی زیر را بر عهده دارد: تعریف ویژگی بخش‌ها (Section)، تعریف جدول بردار، بارگذاری داده و پیکربندی ثبات‌های هسته و حالت کار تراشه و غیره. تعریف ویژگی بخش‌ها اغلب باید همراه نشانی متناظر در فایل LD باشد تا اثر معقول داشته باشد.

۲.۱.۱ تعریف ثابت const در نشانی ثابت

افزودن ناحیۀ حافظه:

FLASH1 (rx) : ORIGIN = 0x0000F000, LENGTH = 2K

تعریف بخش حافظه:

.flash1 : { . = ALIGN(4); *(.flash1); . = ALIGN(4); } >FLASH1 AT>FLASH1

فراخوانی تعریف:

const uint32_t tmp_value __attribute__((section(".flash1"))) = 0x1234567; const uint32_t tmp_value2[2] __attribute__((section(".flash1"))) = {9,8};

۲.۱.۲ تعریف تابع در نشانی ثابت

افزودن ناحیۀ حافظه:

FLASH2 (rx) : ORIGIN = 0x0000F800, LENGTH = 2K

تعریف بخش حافظه:

.flash2 : { . = ALIGN(4); *(.flash2); . = ALIGN(4); } >FLASH2 AT>FLASH2

فراخوانی تعریف:

__attribute__((section(".flash2"))) void GPIO_Toggle_INIT(void) { GPIO_InitTypeDef GPIO_InitStructure = {0}; RCC_PB2PeriphClockCmd(RCC_PB2Periph_GPIOD, ENABLE); GPIO_InitStructure.GPIO_Pin = GPIO_Pin_0; GPIO_InitStructure.GPIO_Mode = GPIO_Mode_Out_PP; GPIO_InitStructure.GPIO_Speed = GPIO_Speed_50MHz; GPIO_Init(GPIOD, &GPIO_InitStructure); }

۲.۱.۳ تعریف متغیر سراسری در نشانی ثابت (بدون مقدار اولیه)

افزودن ناحیۀ حافظه:

RAM1 (xrw) : ORIGIN = 0x20004000, LENGTH = 2K

تعریف بخش حافظه:

.ran1 (NOLOAD) : { . = ALIGN(4); *(.ram1_data); . = ALIGN(4); } >RAM1

فراخوانی تعریف:

__attribute__((section(".ram1_data"))) uint32_t buff_ram1[64]; __attribute__((section(".ram1_data"))) u32 value_ram1;

۲.۱.۴ تعریف متغیر سراسری در نشانی ثابت (با مقدار اولیه)

اگر متغیر سراسری باید مقدار اولیه را حفظ کند، باید روند انتقال در فایل راه‌اندازی تکمیل شود.

افزودن ناحیۀ حافظه:

RAM2 (xrw) : ORIGIN = 0x20004800, LENGTH = 2K

تعریف بخش حافظه و نشانه‌گذاری نشانی انتقال:

.ram2codelalign : { . = ALIGN(4); PROVIDE(_ram2code_lma = .); } >FLASH AT>FLASH .ran2 : { . = ALIGN(4); PROVIDE(_ram2code_vma_start = .); *(.ram2_data); . = ALIGN(4); PROVIDE(_ram2code_vma_end = .); } >RAM2 AT>FLASH

افزودن روند انتقال در فایل راه‌اندازی:

/* Load ram2 data section from flash to RAM */ la a0, _ram2code_lma la a1, _ram2code_vma_start la a2, _ram2code_vma_end bgeu a1, a2, 2f 1: lw t0, (a0) sw t0, (a1) addi a0, a0, 4 addi a1, a1, 4 2:

فراخوانی تعریف؛ مقدار اولیۀ آرایه و متغیر در ناحیۀ RAM بارگذاری می‌شود:

__attribute__((section(".ram2_data"))) uint32_t buff_ram2[64] = {0}; __attribute__((section(".ram2_data"))) u32 value_ram2 = 0x5aa55aa5;

۲.۱.۵ نکات

هنگام تعریف بخش در فایل پیوند می‌توان از KEEP استفاده کرد تا از بهینه‌شدن با گزینۀ پیوند --gc-sections جلوگیری شود، مانند:

KEEP(*(.ram2_data));

متغیرهای سراسریِ مشابه اما بدون عملیات، اگر بخش محل قرارگیری آن‌ها ویژگی KEEP داشته باشد، پس از کامپایل در ناحیۀ حافظۀ هدف نگه داشته می‌شوند و بهینه نخواهند شد.

اگر لازم است ترتیب داخل بخش مربوطه تضمین شود، می‌توان کلیدواژۀ SORT_NONE را افزودن کرد؛ مرتب‌سازی ممنوع می‌شود و اطمینان می‌یابد که بخش‌های ورودی مطابق ترتیب اصلی ظهور در اسکریپت پیوند چیده می‌شوند، مانند:

KEEP(*(SORT_NONE(.ram2_data)))

محتوای برخی بخش‌ها به ترازِ اکید نشانی آغاز نیاز دارد؛ مثلاً جدول بردار معمولاً تراز 1KB دارد؛ می‌توان در LD تنظیم کرد، مانند:

.vector : { . = ALIGN(1024); *(.vector); KEEP(*(SORT_NONE(.vector_handler))) . = ALIGN(4); } >FLASH AT>FLASH

◆۲.۲ راه‌اندازی سرد و گرم

راه‌اندازی سرد و گرم به این معناست که در نخستین روشن‌شدن سیستم، مقداردهی اولیۀ متغیرهای سراسری انجام می‌شود؛ اما هنگام ریست نرم‌افزاری/سخت‌افزاری یا بیداری از خواب می‌توان روند راه‌اندازی را سریع‌تر کرد و پارامترهای اجرا را حفظ نمود؛ مثلاً از روند صفرکردن بخش bss صرف‌نظر شود.

نخست در فایل LD بخشی افزوده شود که متغیرهای سراسری را به RAM منتقل و آرایه را نشانه‌گذاری کند:

.bssjudge : { . = ALIGN(4); PROVIDE( _bssjudge_start = .); KEEP(*(.bssjudge)); PROVIDE( _bssjudge_end = .); . = ALIGN(4); } >RAM AT>FLASH

سپس در فایل راه‌اندازی اضافه شود؛ bssjudgerTab برای پیش‌نگهداری داده مقایسه‌ای است و می‌توان حجم داده در bssjudgerTab را بسته به نیاز افزایش داد:

.section .text.bssjudgerTab,"ax",@progbits .align 1 bssjudgerTab: .byte 0x5 .byte 0xA

پس از پایان انتقال بخش data، انتقال bssjudge و روند مقایسه با محتوای bssjudgerTab افزوده می‌شود؛ اگر محتوای دو طرف هم‌خوان باشد، روند صفرکردن بخش bss رد می‌شود؛ در غیر این صورت در هر ریست، محتوای بخش bss پاک می‌شود.

//load data section end 2: la t0, _bssjudge_start la t1, _bssjudge_end beq t0, t1, 2f la t2, bssjudgerTab bssjudge_func: lb a0, 0(t0) lb a1, 0(t2) bne a0, a1, 2f addi t0, t0, 1 addi t2, t2, 1 bne t0, t1, bssjudge_func j cmdafterbss 2: /* Clear bss section */ la a0, _sbss la a1, _ebss bgeu a0, a1, 2f 1: sw zero, (a0) addi a0, a0, 4 bltu a0, a1, 1b 2: cmdafterbss: //CSR config start

علاوه بر مقایسه با محتوای bssjudgerTab، باید در بخش bssjudge آرایه‌ای از نوع u8 ساخته شود که طول آن دقیقاً با تعداد مقادیر ثابت تعریف‌شده در bssjudgerTab برابر باشد و __attribute__() نیز به آن افزوده شود، به شرح زیر:

__IO uint8_t __attribute__((section(".bssjudge"),unused)) FirstStart[2];

در جریان اجرای برنامه مقدار آرایۀ FirstStart تغییر داده شود؛ اگر با محتوای bssjudgerTab هم‌خوان باشد، پس از ریست از گام صفرکردن bss صرف‌نظر می‌شود:

FirstStart[0] = 0x05; FirstStart[1] = 0x0a;

محتوای بخش bss شامل متغیرهای سراسری/ایستای بدون مقداردهی اولیه و متغیرهای سراسری/ایستای مقداردهی‌شده با 0 است.

فایل راه‌اندازی (Startup)کد اسمبلی آغاز اجرا؛ تعریف ویژگی بخش‌ها، جدول بردار، بارگذاری .data، صفرکردن .bss و پیکربندی ثبات‌های هسته
